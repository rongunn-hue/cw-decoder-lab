2. PIPELINE  (audio in -> text out)  [V]
----------------------------------------
 cw.cpp:179   resampler->process(n, samples, *receiver)   11025 Hz -> 4000 Hz (audio_resampler.h:21, 60 dB stopband)
 receiver.cpp:26 Receiver::feed(), per sample:
   a) ToneFinder::push (tone_finder.cpp:80): 256-pt Hann FFT every 64 samples (64 ms window, 16 ms hop, 15.6 Hz bins)
   b) ToneFinder::analyse (:102): strongest bin in [band_lo..band_hi] (set from CW filter, default 400-1200 Hz);
      noise = 25th percentile of band power, slow-averaged (up 0.003, down 0.01 per frame);
      parabolic interpolation in dB for sub-bin peak frequency; SNR = peak/noise;
      "steady" counter = consecutive frames with peak >= 15.5 dB over noise within +-1 bin.
      Optional APF (radio's peak filter) response divided out (apf_gain2, :17).
   c) ToneLock::follow (tone_lock.cpp:104): retunes NCO to FFT peak only if peak steady >= 2 frames, is >= 2 bins
      from lock, and the current station is judged gone (no energy 1 s) or only a skirt of a stronger station
      ("elsewhere_" counter, 12 dB rule, 32 count = ~0.5 s key-down).
   d) ToneLock::push (:128): real input x NCO (complex mix to 0 Hz) -> 81-tap Kaiser FIR LPF, 100 Hz cutoff ->
      mean of last 64 complex baseband samples (16 ms) every 32 samples (8 ms) -> power = |mean|^2.
      This 8 ms step is the time base of everything downstream (STEP_MS = 8, rx_defs.h).
   e) ToneLock::every_4_steps (:164): PLL phase-error update on 4-step (32 ms) means, pull scaled by run SNR
      (0 at SNR 2, full at 5), only between two "alive" runs; alive = smoothed power/noise > 4.
   f) KeyDetector::step (key_detector.cpp:40): r = power/noise. Carrier floor = 5th percentile of r over first
      125 steps (1 s, during which output is muted) then quantile-tracked; if key down > 60 steps (480 ms) floor
      rises 5%/step (treated as carrier). Effective noise scaled up when carrier floor > 2x expected.
      schmitt (:79): on-threshold = max(peak-3 dB, user floor dB); off-threshold = max(peak-6 dB, floor-3 dB);
      peak decays 0.97/step key-down, 0.94/step key-up. Edge needs 2 consecutive steps over threshold
      (3 after >=400 ms quiet). crossing() (:142) interpolates the edge time within the step using sqrt(power)
      (amplitude) ramp -> back_ms. "strong" flag = mark peaked floor+3 dB.
   g) ElementTimer::step (element_timer.cpp:243): accumulates run length in ms, splits the edge step by back_ms;
      close() (:219) classifies: mark < 2.0*dot = DIT else DAH; gap < 1.7*dot = element gap, < 5*dot (or
      Farnsworth-adjusted) = char gap, else word gap.
      Held-mark logic: the first mark after a word gap is held until more keying follows (lone weak blip dropped,
      lone strong mark >= 0.7 dot becomes a one-element word at word gap). Mark > 8 dots = carrier, ignored.
      End-of-text: no mark for max(5*char_from, 200 ms, word_from) -> synthetic WORD_GAP so last char flushes.
   h) MorseText::put (morse_text.cpp:32): '.'/'-' appended (max 12); CHAR_GAP -> flush(); WORD_GAP -> flush + one
      space (never two). Unknown code -> "<?>".  Table lookup morse_code.c:46.
   i) cw.cpp:241 on_text -> squelch (cw.cpp:183) -> cw_decoder_text() -> panel / remote server.

3. TIMING / SPEED ESTIMATION  [V]
---------------------------------
 - Speed state is a single dot length dot_ms_ (start 60 ms = 20 WPM; clamp 24..120 ms = 50..10 WPM;
   trainer mode up to 240 ms = 5 WPM).
 - learn() (element_timer.cpp:143): every closed mark AND gap length is added to a 300-slot histogram (4 ms/slot,
   to 1.2 s), each entry smeared as a +-4 slot triangle; all entries age x0.9 per new entry.
 - dot_estimate() (:175): finds the lowest-length peak (>= 8% of top), then the next cluster starting >= 1.7x that,
   takes the centre of mass of everything from 0 to the valley between. Marks and element gaps share the
   lowest cluster (marks measured long, gaps short, so centre of mass balances them).
 - set_dot() (:90): estimate within 25% of dot_ms_ -> low-pass (gain 0.3). Further than 25% -> candidate new speed,
   needs histogram >= 8 entries, must be confirmed by a stricter (25%-peak) estimate, and 3 consecutive agreeing
   estimates, then the histogram is cleared and dot_ms_ set outright.
 - Thresholds are FIXED RATIOS of the single dot estimate: dit/dah 2.0, char gap 1.7, word gap 5.0.
   Farnsworth: median of last 16 character gaps (>=8 needed) can raise the word boundary: 5/3*(gap-dot), cap 3 s.
 - No per-element adaptive thresholds, no dah/dit ratio estimate, no lookahead, no Viterbi/HMM, no dictionary.

4. DSP SUMMARY  [V]
-------------------
 FFT (liquid fft_create_plan, Hann, 256), 25th-percentile noise estimator, NCO + 81-tap Kaiser LPF + boxcar
 integrator, Costas-like PLL on 32 ms means (cross product phase error), power Schmitt trigger with peak-following
 thresholds, quantile carrier floor. No Goertzel. No bandpass beyond the 100 Hz baseband LPF.

5. CONFIDENCE / NOISE REJECTION  [V]
------------------------------------
 - Dec SNR user threshold (default 5 dB in Receiver ctor, receiver.cpp:17; UI default 8 per MANUAL.md) = floor_db.
 - 1 s mute after tone change/reset.
 - Lone-mark rejection (held mark, strong flag), carrier rejection (>8 dots, key-detector carrier floor).
 - Tone-lock liveness: station dropped only after ~1 s absence.
 - Squelch in cw.cpp:183 (not in the decoder core): a character is "good" when mean keyed SNR >= floor + 5 dB;
   opens after 3 good chars, closes after 2 bad, or 3 s idle; weak chars held pending and printed only if a good
   one follows.
 - NO per-character confidence output, NO error correction, NO spell/callsign/dictionary correction.
   Output for an unknown pattern is the literal "<?>". "<ERR>" for 6-8 dots.

7. LIMITATIONS RELEVANT TO HAND-SENT MORSE  [V from code; effect on real audio is H until tested]
-------------------------------------------------------------------------------------------------
 - Single global dot length with fixed ratio thresholds (2.0 / 1.7 / 5.0). Hand-sent dah/dit ratios vary (2-4+) and
   a "bug"/swing sender has short dits and long dahs; the dit/dah boundary at 2 dots can fail for sloppy senders.
 - Speed learning requires 3 consecutive agreeing estimates after >=8 histogram entries to change by >25%, so
   abrupt speed changes lag by a number of elements; a slowing/accelerating hand sender is tracked only by the 0.3
   smoothing within 25%.
 - Marks and gaps pooled into one histogram cluster assumes marks ~ dot + epsilon and element gaps ~ dot; irregular
   hand-sent element gaps pollute the dot estimate.
 - Character gap threshold 1.7 dots is intentionally short: hand senders with long intra-character gaps will be
   split into extra characters; short inter-character gaps will be merged. No contextual correction.
 - Hard decisions per element at the time of the edge; no retroactive re-segmentation when speed estimate later
   moves; no alternatives/probabilities carried to the text stage.
 - Morse table fixed; unknown -> "<?>", no fuzzy matching (e.g. nearest valid code).
 - Tracks ONE tone; 1 s mute on start; 100 Hz baseband LPF (+-100 Hz) and 8 ms step bound the maximum speed and
   edge-time resolution (STEP_MS=8; sub-step interpolation partly compensates). Max speed clamp 50 WPM.
 - Carrier/lone-blip rules were tuned for >= 10 WPM (comment in element_timer.h, trainer_range).
 - Noise floor is the 25th percentile of the FFT band: with other strong CW signals in-band this is biased [H].
 - The squelch lives outside the core and is tuned for HF noise; it can swallow weak real text [H].
 - X6100 coupling: first-second mute, VFO-follow, APF compensation, trainer hooks are in the core classes.

8. EXTRACTABILITY FOR STANDALONE LINUX  [V for dependencies; H for effort]
--------------------------------------------------------------------------
 Highly extractable. The core (src/cw_decoder/*) is self-contained C++17 with the only external dependency
 liquid-dsp (fft, nco_crcf, firfilt_crcf, msresamp_rrrf) - available on Linux (libliquid-dev). No LVGL, no radio
 code, no threads in the core. Interface is Receiver(TextFn, KeyFn, StepFn) + feed(const float*, n) at 4000 Hz.
 To replace or remove:
  - audio_resampler.h assumes 11025 in; replace with any resampler to 4000 Hz (or use liquid msresamp for any rate
    from 8000/44100/48000; "downsampling only" per its own comment).
  - cw.cpp: all of it is app glue (cfg_sm settings subscriptions, atomics, AUDIO_CAPTURE_RATE, squelch). The
    squelch (cw.cpp:183-240) is portable logic and could be copied; the rest replaced by a small main().
  - cw_decoder.c / panel / remote_server: replace with stdout.
  - Trainer-only hooks (expect, own, turn, trainer_range, ours) can be left unused or removed.
  - CMake: src/cw_decoder/CMakeLists.txt builds a static lib with only liquid as dependency.
 Test assets: tools/cw_trainer/cw_trainer_test.cpp is a host test harness that already runs the real decoder on
 synthetic keyed audio (see its Makefile). [V that it exists; not run.] There is NO tests/cw_decoder directory in
 this commit although the CMakeLists comment refers to one [V].

A3. WHAT OPENX6X00 ADDS  (absent upstream)  [V]

    new_tone()/turn()/ours()/expect()/trainer_range() hooks, 5 WPM floor in trainer mode.

    veto).
 4. Text stage: strcmp table instead of binary tree; unknown code -> "<?>" (upstream: ERR string for tree miss);

A5. CONCLUSIONS FOR THE STANDALONE-DECODER GOAL
 - Neither version contains Bayesian/probabilistic decoding, language modelling or retroactive re-segmentation; the
   "bayes" directory name in upstream history did not survive in the code I read. [V]
 - The algorithm that matters for hand-sent Morse (single dot estimate, fixed 2.0/1.7/5.0 ratios, hard per-element
   decisions) is identical in both. Section 7 limitations therefore apply to upstream too.
 - Best base for extraction: OpenX6X00's version has better noise/carrier rejection; upstream's has tests,
   diagnostics hooks and a cleaner header-only structure. Taking OpenX6X00's core plus upstream's tests/inspector
   approach is reasonable. [H]
 - Still to do: read the remaining part of R1CBU's 2023 decoder if a baseline of "what hand-sent CW looked like to the
   original" matters; locate IU1WXY v0.127 source to confirm no IU1WXY-specific changes.

ADDENDUM B — TIMING-STAGE EXPERIMENT (simulation; NOT real recordings)
==============================================================================
Code: ~/Chat-Projects/cwlab/timing_lab.py, diag.py, viterbi.py (my own Python; liquid-dsp build was not permitted, so the
DSP front end was NOT run). timing_lab.py is a port of ElementTimer close/learn/dot_estimate/set_dot/retime from
element_timer.cpp as read; the held-first-mark/carrier/lone-mark logic is OMITTED. Input = detector-style intervals
(8 ms grid, marks +6 ms, gaps -6 ms, 3 ms noise). Sender model = my assumption: lognormal jitter on every element,
dah ratio ~N(r, sd), gap means/sd as listed, random-walk speed drift. Text: random ham words (12 words/trial).
Scores = character error rate (Levenshtein/len). 25 trials/scenario; seeds fixed.

Where the current timer errs (good-hand scenario, per-decision error rates, diag.py):
  element gap read as char gap 3.7% (splits letters), dit->dah 3.9%, dah->dit 2.8%, char gap->word gap 4.5%,
  word gap->char gap 5.1%. With ~2.5 elements/char these compound to ~20-25% CER. Each is a HARD threshold at a fixed
  multiple of ONE pooled dot estimate (2.0 / 1.7 / 5.0).

CER %            current(port)  local-cluster(2-pass)  viterbi+params
good hand            25.3            17.5                  12.4
sloppy hand          84.1            46.7                  34.4
bug swing            60.6            13.0                  10.4
fast 28 wpm          21.2            20.4                  15.4
slow 10 wpm          34.9            18.0                  12.2
tight 2.2/5 dots     51.7            43.3                  45.9   (viterbi worse than local-cluster here)
drift 4%/elem        26.4            19.2                  15.2
Farnsworth x1.8      39.5             8.2                   7.4

What the two alternatives do (both separate dit/dah, element/char/word gap models, no fixed ratio constants):
  local-cluster: per-interval thresholds from 2-means on marks and log-domain 2-means on gaps in a +-12 interval window.
  viterbi+params: same local parameter estimates, but NO hard decisions: lognormal likelihood of every interval under
  {dit,dah} / {element,char,word gap}, joint beam search over characters (state = partial code), letter-frequency
  unigram prior, invalid code penalty. Equivalent to removing the hard-threshold stage.
Caveats (all real): windows are non-causal (+-14 intervals, ~1-3 s of added delay); sender model is mine and may differ
from real operators; the unigram prior is tiny; the comparison port lacks the held-mark logic; no noise/DSP errors are
included (key detector misses/glitches would add errors to every decoder); "tight 2.2/5" shows the gap models still fail
when char/element gaps genuinely overlap. These numbers are evidence for WHERE to change the code, not a claim of
real-world accuracy.

ELEMENTAL CHANGES SUGGESTED BY THE CODE READ + EXPERIMENT (hypotheses until tested on real audio)
 1. Replace hard dit/dah and gap thresholds (ElementTimer::close, element_timer.cpp:219) with likelihoods; decode a
    character/word jointly (Viterbi/beam) instead of emitting at each gap. Largest measured gain.
 2. Estimate dit, dah, element-gap, char-gap and word-gap centres SEPARATELY (marks and gaps are pooled into one
    cluster today, dot_estimate() :175), so dah ratio and sloppy/short gaps stop corrupting the threshold.
 3. Carry per-interval softness out of the detector (duration uncertainty, mark SNR, edge-quality) into the likelihood;
    today KeyEdge only has dir/back_ms/strong.
 4. Allow retroactive re-segmentation: keep a short interval history and re-decode the last word when the speed/ratio
    estimate moves (a speed change costs several elements today: relock needs 3 confirmations).
 5. Add language prior (letter n-gram, callsign/Q-code/prosign patterns) as the Viterbi path score; invalid codes become
    low-probability paths instead of "<?>".
 6. Front end (unchanged, but note): 8 ms step + 6 ms edge bias are small next to hand-sent jitter; the DSP chain is

ADDENDUM C — LITERATURE ON HAND-SENT TIMING STATISTICS (for building a facsimile)
==============================================================================
No public dataset of per-element hand-sent timing, and no published per-operator parameter tables, were found.
Best sources located (all read by me unless noted):
 1. E. L. Bell, "Optimal Bayesian estimation of the state of a probabilistically mapped memory-conditional Markov
    process with application to manual Morse decoding", NPS thesis, Sept 1977, handle 10945/26668.
    PDF + text saved: ~/Chat-Projects/cwlab/refs/bell1977.pdf / bell1977.txt. Key statements [V]:
    - "when normalized for speed variation, the density of each symbol duration, averaged over several operators,
      approaches the gaussian density. For individual operators, however, the densities are far from gaussian, and no
      single normalizing technique was found ... estimation of these highly individualistic densities must be
      accomplished on-line" (ca. line 5815).
    - Model: instantaneous element duration A per symbol; dot=elem space=A, dash=char space=3A, word space=7A,
      pause=14A; speed-normalised durations modelled as Laplacian (double-sided exponential) about the nominal
      multiple, with parameters chosen so P(dot read as dash)=1.35% at optimum threshold (ca. line 6060). The 1.35% is
      stated as the average error over "55 samples of hand-keyed Morse studied in the TSC analysis".
    - Dependence on past symbols is present even for straight keys: reduced variability of element-space duration when
      the preceding symbol was a dot (ca. line 5715); stronger for bugs and electronic bugs.
    - Field test: HKM (hand-keyed) samples 16-22 wpm at 16-20 dB SNR: letter error 3-15% with his tree decoder
      (Table XXII, 4 samples). KAM (machine) 28-35 wpm: 1-10%.
 2. TSC report cited by Bell: A. Meisel et al., "Morse Laboratory Data Analysis Report", Technology Services
    Corporation, May 1976 (the 55-sample hand-keyed study). NOT located online; likely the source of the real numbers.
 3. PDP-12 project, "Machine Recognition of hand-sent Morse Code using the PDP-12 Computer"
    (alanpich.github.io/Morse-Code-Recognition/): three 10-15 min recordings; qualitative only in the page read:
    character and word spaces have large variance and overlap heavily (cannot be separated by a time threshold);
    dot/dash and symbol-space/other-space are separated by a wide gap; dash is longer when followed by a character or
    word space; symbol-space shortens as the preceding dash lengthens; variance is NOT a speed-drift trend. Numbers
    are in appendices not retrieved. Sub-pages (data-analysis/pulse-algorithm.html, space-algorithm.html) not read.
 4. C. R. Blair, "On Computer Transcription of Manual Morse", JACM (doi 10.1145/320986.320997): fetch blocked (403);
    not read.
 5. AG1LE blog (2013) histograms of ~1800 symbols off-air on 7 MHz: dit ~0.1, dah ~0.3, element space ~0.1, char
    space ~0.3, word space ~0.6-0.7 (normalised to a 10-dit cap); no spreads or raw data published. Bell's thesis is the
    basis of AG1LE's fldigi Bayesian decoder (code on GitHub, not examined).
IMPLICATIONS FOR timing_lab.py's sender model (currently independent lognormal jitter per element):
 - add per-symbol instantaneous speed (random walk) rather than one drift per element;
 - heavy-tailed (Laplacian) deviations, not Gaussian/lognormal;
 - dependence on the previous symbol (space after dot less variable; space after long dash shorter; dash longer
   before char/word space);
 - char-gap and word-gap populations that overlap;
 - per-operator parameter sets (key type: straight / bug / electronic).
 Absolute parameter values must still be calibrated from real recordings (own, or the TSC report if obtainable).
